## Premise Challenge (Step 0A)

### Is this the right problem to solve?

The founder's stated problem: *"AI output quality isn't 100%, chunks if big, doesn't work 100% correctly, I have to check every time."*

**Three re-framings were considered:**

1. **"Build an AI tool that follows SDLC"** (the founder's literal ask)
   → Rejected. SDLC is paperwork for teams; AI doesn't need requirements docs and sign-off. The framing is wrong.

2. **"Build a better agent harness"** (compete with `claude-code` / `opencode`)
   → Rejected. Three credible agents already exist; the founder's pain is NOT the harness, it's the lack of a shared standard for "done."

3. **"Define a collaboration-grade protocol + reference skill"** (chosen)
   → Wins. A protocol is small, forkable, opinionated, and lets anyone participate without adopting a vendor. This matches the founder's stated goal of a public GitHub repo for collaboration.

### Actual user/business outcome

The founder wants to stop manually re-checking every AI output AND wants other people to collaborate on solving this. A protocol achieves both: if adopted by the founder's own agent, his manual-check pain drops; if adopted by others, the founder attracts collaborators.

### What if we do nothing?

The founder keeps using `claude-code` / `opencode` as-is. Pain persists. No public artifact, no collaborators. The "I tried, quality isn't good enough" stays the same.

**Verdict:** Doing nothing is acceptable but suboptimal. The cost-to-launch is low enough that even a private dogfooded version pays off.

## Implementation Alternatives (Step 0C-bis) — MANDATORY

**APPROACH A: Minimal Viable (Protocol + 1 example)**
- **Summary:** A `PROTOCOL.md` defining the 5 gates + a `SKILL.md` implementing them + 1 worked example in Python. No templates, no CONTRIBUTING.md.
- **Effort:** S (1-2 days)
- **Risk:** Low — small surface, dogfooded before publish
- **Pros:** Ship Friday. Founder can iterate in private. Lowest bar for first contributors (just write a worked example).
- **Cons:** Too thin to be useful immediately; contributors hit "what format?" friction.
- **Reuses:** Existing SKILL.md format from founder's other skills.

**APPROACH B: Recommended (Protocol + skill + templates + 3 examples)**
- **Summary:** Above + `templates/` (task, DONE, PR) + 3 worked examples (Python, PHP, Node) + CONTRIBUTING.md + LICENSE.
- **Effort:** S-M (3-5 days)
- **Risk:** Low-Med — more surface to maintain, but each piece is small
- **Pros:** Self-contained. Contributors can fork and immediately try. Multi-language signals "not a one-person project." Templates make adoption one-command.
- **Cons:** 5-day build before any dogfood. Founder delays shipping.
- **Reuses:** Same as A.

**APPROACH C: Ideal Architecture (Protocol + spec test suite + CI + website)**
- **Summary:** Above + a JSON-schema test that validates DONE.md + a GitHub Action that fails PRs missing gates + a docs site (mkdocs or docusaurus) + Discord community.
- **Effort:** L (2-3 weeks)
- **Risk:** Med-High — over-engineering for a 0-contributor project. Maintenance burden before product-market fit.
- **Pros:** "Looks serious" — attracts more contributors. Validates that the protocol is implementable.
- **Cons:** 80% of the work has zero users. Founder already runs thin on time across Specboard/Calora/Qalam.
- **Reuses:** Founder's existing Dokploy + CF infra could host the site cheaply, but adds maintenance.

**RECOMMENDATION: Approach B** because:
1. The marginal value of templates + multi-language examples over Approach A is high (1 collaborator-facing docs gap closed) for ~3 extra days of effort.
2. Approach C's CI/spec-validation/web-website investment is wasted on a project with 0 contributors; ship the body, not the chrome.
3. The founder's actual goal is a **collaboration target**, not a website — Approach B gives them a usable, forkable, demo-able artifact.

## Vision (Step 0D-prelude + 0D)

### 10x Check

The version that's 10x more ambitious: the protocol becomes a **layer** that any agent harness can opt into via a one-line config, with a public dashboard showing which repos enforce which gates. By month 12, "ai-sdlc compliant" is a GitHub badge.

**Why we're not doing that version:** Founder has 0 collaborators and 1 user (himself). Building the layer before proving the protocol is the cart-before-horse. Ship the protocol, see if anyone shows up, *then* build the layer.

### Platonic Ideal

A new contributor visits the repo on a Saturday morning, reads `PROTOCOL.md` in 5 minutes, runs the Python example, and submits a PR by Sunday evening adding a Ruby example. They never asked a question. The CONTRIBUTING.md told them everything.

## Accepted Scope

2. `SKILL.md` — Hermes/OpenCode/Claude-Code skill, ~200 lines, executable

## Temporal Interrogation (Step 0E)

What the implementer (a fresh agent loading this plan + protocol) will hit:

| Hour | Decision needed now |
|------|---------------------|
| 1 (foundations) | **Is the 5-gate list complete?** — We've identified Spec/Scope/Verify/Context/Done. Missing: a **"rollback gate"** — what does the agent do when its changes break something mid-task? Add a 6th gate: **Recovery gate — agent must be able to undo its last change without manual intervention.** Decide: include in v0.1 or defer? **Recommendation: include; it's a one-line addition to DONE.md and dramatically reduces the founder's actual lived pain.** |
| 2-3 (core logic) | **How strict is "scope" gate?** Strict = forbid any unrequested file; Loose = forbid new modules but allow small in-file changes. Recommendation: Loose (matches how humans review PRs). |
| 4-5 (integration) | **How does the skill signal "I passed all 5" vs "I failed gate 3"?** Recommendation: DONE.md has 5 checkboxes; unchecked = failure; the skill exits with explicit `STATUS: PASS` or `STATUS: FAIL gate-N` so any harness can read it. |
| 6+ (polish/tests) | **What's the test for the protocol itself?** A small Python script that walks through the Python example end-to-end and asserts all 5 gates pass. Lives at `tests/test_python_example.py`. |

## Definitions / Glossary

- **Gate** — a verifiable condition the AI agent must satisfy before declaring a task done.
- **Protocol** — the spec document `PROTOCOL.md`; normative, language-agnostic.
- **Skill** — `SKILL.md`; the harness-specific consumer of the protocol (Hermes, OpenCode, Claude-Code, etc).
- **Worked example** — a real coding task demonstrated end-to-end with gate evidence.
- **DONE.md** — the gate checklist the agent fills in at task completion.
